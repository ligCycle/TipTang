# PK in one stream (P9a) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (inline, opus reviewer per task or batched when usage is tight). Steps use checkbox (`- [ ]`) syntax.

**Goal:** A creator starts a timed PK with two named sides. Fans choose a side on the donate page while it runs. The OBS link `/overlay/<u>/pk` shows a split bar, the totals and a countdown, then the winner. The result is frozen a grace period after the end.

**Architecture:**
- Pure rules are in `src/lib/pk.ts` (done).
- The server lives in `src/lib/pk-server.ts`: start, end early, freeze under the creator lock, feeds, and cancel when the card goes off or the account is deleted.
- Totals come from a groupBy over confirmed tips (Q1). Nothing hooks into the tip pipeline (Q3).

**Spec:** `docs/superpowers/specs/2026-10-24-pk-design.md`. Rulings Q1–Q12 override.

## Global Constraints

- **Copy:** th/en parity, no emoji, gender-neutral.
- **Schema:** goes into the feature_hub migration. Include the P9b fields now (`opponentId`, `pkInvitesOff`) so P9b adds no new columns.
- **Locks:** lock order is Tip → Wheel → User. PK code never runs inside a tip transaction.
- **Never:** print overlay keys, use the production DB, or push.

## Review Focus

1. Two feeds freezing at the same moment end the match once, with the same totals. A confirm during the freeze is counted or not, never half (Q3).
2. A fan can't put a tip on another creator's match, an ended match, or a cancelled one (Q5).
3. Turning the card off, or deleting the account, cancels a running match. The overlay hides it and history keeps it (Q8, Q9).
4. Grace is 60 s for auto-confirm and 5 min for manual (Q4). The page says confirms after the freeze don't count.
5. The countdown uses `serverNow`, so it stays right when the viewer's clock is off (Q10).

- `src/app/api/account/route.ts` (cancel before delete)
- `src/app/api/overlay/asset/route.ts` (`pkToggle`)
- registry, presets, setup, hub

**Schema:**
- `enum PkStatus {PENDING ACTIVE ENDED CANCELLED DECLINED}`.
- `PkMatch`: `{id, kind, ownerId? (SetNull), opponentId? (SetNull), status, nameA, nameB, colorA, colorB, durationSec, graceSec, startedAt?, endsAt?, endedAt?, totalA?, totalB?, createdAt}`, with `@@index([ownerId, status])` and `@@index([opponentId, status])`.
- User: `pkEnabled false`, `pkInvitesOff false`, plus two relations.
- Tip: `pkMatchId String?`, `pkSide String?`, `@@index([pkMatchId, status])`, `@@index([creatorId, status, createdAt])`.

**`pk-server.ts`:**
- `startSolo(userId, {nameA, nameB, colorA, colorB, durationSec}, now)`: under `lockCreator`. Refuses (409 `busy`) if there is an ACTIVE match involving the user. `graceSec` = `autoConfirmTips` ? 60 : 300.
- `endEarly(userId, now)`: sets `endsAt = now` on the user's ACTIVE solo match.
- `freezeIfDue(matchId, now)`: Q3 transaction (`lockCreator`s in id order, then `PkMatch FOR UPDATE`, then a status/time check, then SUM rounded to whole baht, then update).
- `soloTotals(matchId)`: groupBy `pkSide`.
- `currentFor(userId, now)`: the latest match involving the user that is ACTIVE, or ENDED with `endedAt` within the last 15 s plus grace. It freezes if due. Returns the feed shape `{kind, nameA, nameB, colorA, colorB, totalA, totalB, endsAt, status, winner, serverNow}`.
- `history(userId)`: the last 10.
- `cancelAll(tx, userId, now)`: cancels PENDING and ACTIVE matches, storing totals.
- `fanMatch(creatorId, matchId, side, now)`: returns the validated id/side or null (Q5).
